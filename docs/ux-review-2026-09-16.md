# Chatrock UX review — 16 September 2026

Scope: source review of frontend navigation, projects, composer, settings, memory,
sharing, and feedback; backend project/chat APIs, preferences, context assembly,
search, and enrichment; relevant ADRs and tests. Findings below describe the
checked-out implementation. This was not an authenticated walkthrough of the live
deployment or an observed usability study. Proposed changes are recommendations,
not accepted architecture decisions.

**Main recommendation**

Make the app revolve around three tasks: continue a conversation, start a
conversation, and find previous work. A project supplies the shared context for
those tasks. Today the user has to navigate separate organizational modes, infer
what the assistant knows, and understand several interacting settings.

Simplification should reduce those decisions and make the remaining controls
truthful. Several apparent usability problems are frontend/backend contract bugs;
changing the layout alone will leave those problems in place.

The app already has useful foundations: editable summaries and memories, project
file summaries, context retrieval tools, recent-activity sorting for chats,
context-aware creation entry points, and substantial chat reconnection recovery.
The older `TODO-projects-issues.md` partly describes features that now exist.
Refine these capabilities rather than treating every old TODO as missing work.

These are source-confirmed paths and omissions. The exact visual manifestation
should be reproduced in regression tests during implementation.

**A simpler navigation model**

Replace the four-mode activity rail with one sidebar:

- New chat and Search at the top.
- Recent chats, including project chats with a small project label.
- Projects, optionally expandable to a short list of recent chats.
- Settings at the bottom, including personal memory management.

This removes the need to switch modes simply to find a conversation. Currently
the default Chats filter excludes project chats, so moving a chat can make it
disappear. Starting a new chat switches back to the Chats panel even within a
project. Project expansion also navigates, and opening a project chat does not
always establish the corresponding expanded project.

Keep expansion and navigation separate: the chevron expands; the project name
opens the project. Use the route as the source of selection. Keep private-chat
visibility separate from ordinary list preferences.

The project sidebar should provide navigation, with full files and memories
managed on the project page. Its current nested Files/Memory tree duplicates the
page, truncates content into narrow rows, and keeps separate caches that become
stale. Removing that duplication also removes state synchronization work.

Project ordering is already creation-based through descending ULID keys. For
recent project activity, derive a timestamp from loaded member chats initially;
add durable activity metadata only if required by pagination or scale.

**Make the project home a place to work**

Lead with the project name, a short description, and a composer for starting a
project chat. Show recent conversations immediately below. Put a clear
“Add existing chats” action here so organization can start from the destination,
with multi-select if needed.

Use a compact “Knowledge” area for files, instructions, and saved project facts.
Give these separate sections within that area so their different roles remain
understandable. Keep description/instructions discoverable without making the
user open a settings dialog just to learn what the project is about.

The current page stacks every chat, then every file, then every memory. As a
project grows, frequent tasks require scrolling through unrelated content.
Use short previews with “View all” and a searchable full list. Start with the
minimum layout needed; avoid adding a dashboard of generated status cards,
tasks, milestones, and activity feeds without evidence that users need them.

Empty projects should explain the benefit in one sentence and offer three
concrete actions: start chatting, add files, set instructions. Only a name is
required to create a project. Use an explicit Create action; creating on input
blur makes clicking away a surprising commit.

**Make knowledge use understandable and controllable**

Files, instructions, and memories currently have distinct behaviors that the
interface scarcely explains:

| Item | Plain-language role | Suggested user action |
| --- | --- | --- |
| Instructions | How the assistant should work in this project | Edit instructions |
| Files | Material the assistant can consult | Open, replace, remove, choose usage |
| Saved facts | Information carried forward between chats | Add, edit, remove, inspect source |
| Other chats | Previous work the assistant can consult | Find or explicitly reference a chat |

Keep automatic file consultation as the default. Replace `auto / always / never`
with “Use when relevant / Include in every message / Exclude from AI context,”
after implementing those semantics. Advanced inclusion belongs in a file menu
or detail view rather than a dropdown on every row.

Add real file opening/download and a detail view; currently clicking a filename
expands its summary. Include status, size, and useful processing errors.
Deep links should open or scroll to the actual file; the current `?file=` route
only expands/highlights it below the chat list.

Allow a user to reference a particular file or prior chat from the composer.
This supplies a direct answer to “use this material” without requiring the user
to trust automatic selection. Offer “Save to project” for a useful chat
attachment or answer, reusing the file infrastructure.

Separate “available to consult” from “actually consulted.” A compact, expandable
sources/context indicator can show instructions enabled, available files, and
the files/chats read for an answer. Persist essential usage metadata so this
continues to work after reconnecting.

“Always” currently has a 20,000-character per-file slice and an 80,000-character
total check that counts original lengths before slicing; it can skip a file
entirely even when a slice would fit. The manifest also caps files at 50 and
sibling chats at 30. Communicate partial coverage and provide retrieval beyond
the manifest instead of presenting these limits as comprehensive knowledge.

Memories need a manual Add action and source links. The current model allows
automatic reconciliation to rewrite or delete existing entries, including
user-edited ones; it records no provenance or user-lock distinction. Initially,
distinguish user-maintained facts from automatically maintained facts. Likewise,
make user notes separate from generated chat summaries so later summarization
does not silently rewrite intentional notes. Removing a chat from a project
should explain what happens to facts previously learned from it; provenance is
needed before reliable automatic retraction can be offered.

**Make search behave like finding things**

The current header search navigates to a new chat and sends the query through
the model with a forced history-search tool call. Every search becomes another
conversation. Search only considers chats with summaries; it caps the combined
corpus at 200 entries and file discovery at 20 projects. Because chats are
concatenated before files, enough chats can crowd all files out. Ranking failures
also return the same empty array as no matches.

Provide a search overlay/page that preserves the current conversation, shows
ordinary clickable results, and visibly selects “Everywhere” or a project.
Offer “Ask about these results” as a subsequent action.

Start with immediate title/filename/topic matching over loaded data, then add a
paginated backend search route as needed. Reuse the existing semantic search for
meaning-based discovery. Show loading, unavailable, no matches, and partial
coverage distinctly. A vector database is not a prerequisite for fixing the
basic navigation workflow.

**Reduce the settings users must understand**

The composer currently combines model, thinking effort, research depth, project,
and Private. On mobile several choices shrink to short labels or icons. Two
independent effort scales make a routine question require knowledge of reasoning
and tool budgets.

Keep the model selector and one visible response mode, initially something like
“Standard / Research.” Keep detailed effort controls in an expanded menu and
preserve existing capabilities there. Before implementing presets, define their
mapping and validate it with representative tasks; do not silently alter the
meaning of existing saved choices.

Move project assignment to a consistent header/context control usable for both
drafts and saved chats. The existing draft-only picker and sidebar-only move
menu make the same action live in different places before and after sending.

Use these homes for settings:

- Personal settings: global defaults and personal memory.
- Project knowledge: instructions, files, and facts.
- Project/chat options: occasional overrides, initially collapsed.
- Composer: choices relevant to the message being sent.

Show inherited values honestly, e.g. “Answer length: Concise · From project,”
with “Use project default” to clear an override. Resolve
user → project → chat → current-message settings once rather than independently
materializing defaults across entry points.

Move provider selection, Browser Core/Extended, timestamp injection, and token
statistics under Advanced. Use user-facing labels such as “Browse websites”
and “Interact with websites” where an explicit capability choice matters.
Remove internal tool names, ADR paths, and TTL terminology from product help.

Privacy needs concise explanations: whether saved knowledge is read, whether
new knowledge is saved, whether the chat is discoverable, and when it is
deleted. The current “Update memory” control also affects summaries, search,
and list visibility; the Private shortcut combines two flags but still allows
reading existing memory. Keep granular control available, but do not make a
single “Private” label carry those unspoken meanings.

Turning off memory currently gates automatic titles and summaries as well
(`sendMessage.ts` post-turn block). Separate organization from learning about
the user, subject to the explicit sensitive-chat policy.

**Make everyday interactions consistent**

Use one visible overflow menu on chat/project/file rows for infrequent actions.
Repeated rename, retitle, delete, and move icons add density, while hover-only
revelation is hard to discover with touch or a keyboard. On messages, keep the
most common actions nearby and put branch deletion/forking in a labeled menu.
Use “Try again” and “Branch into new chat” with a clear variant indicator.
Forking is reversible and need not have a confirmation dialog.

Expose Share/Export through chat actions; currently sharing sits inside the
settings dialog's third tab. Default sharing to a snapshot, with a clear option
for a link that includes future changes. Keep advanced export/tool/thinking
choices collapsed, and provide a preview of what the recipient will see.

Use one save convention. Inline edits need visible edit affordances and a
reliable save/cancel path; clicking summaries currently edits them while
clicking the enclosing row navigates. Failed saves should retain the edit and
offer retry. Moves and removals should offer Undo where the backend can
actually restore them. Permanent deletion still needs accurate confirmation.

Load failures should remain visible in the affected section with Retry.
`ProjectView` silently ignores file/memory errors and redirects to a new chat
on any project fetch failure. `MemoryPanel` can show an empty state after a
failed read. A disappearing 3.5-second toast is insufficient for an unsaved
edit or failed upload.

Reuse the existing chat recovery principles for files and project enrichment:
durable status, bounded stale states, and refetch after resuming. Synchronize
project metadata/chats/files/memory through one query cache or normalized store,
with cancellation of requests for a previous project. `ProjectView` currently
ignores the project metadata returned by `getProject` and uses a separate list
cache instead.

Accessibility is part of this cleanup: real links/buttons for navigation,
keyboard-operable menus, focus visibility, and dialog focus management.
`Dialog.tsx` currently has neither dialog semantics nor focus trapping/restoration;
global creation buttons also have `tabIndex={-1}`. These are concrete barriers,
not just visual preferences.

**Suggested delivery order**

| Slice | Scope | Completion criteria |
| --- | --- | --- |
| 1. Restore predictable behavior | Privacy enforcement, project DTO/default reset, memory gating, deletion contract, mobile navigation, draft creation, upload recovery, settings saves, branch-correct retrieval | Reload preserves choices; all plus buttons behave alike; project deletion keeps chats visibly; private content stays isolated; errors can be recovered without a full reload. |
| 2. Simplify common journeys | One sidebar, project-aware composer, project home, destination-side add chats, ordinary search, shared menus/settings conventions | A user can create a project, start a chat, move an existing chat, find it again, and return on mobile without mode hunting or accidental empty chats. |
| 3. Improve shared knowledge | File opening/replacement, explicit references, context-use feedback, provenance and manual facts, honest inclusion/coverage | Users can tell what the assistant used, deliberately supply a source, correct durable knowledge, and recover after backgrounding an upload. |

Write ADRs alongside implementation for the navigation model, replacement of ADR
0018's dual creation behavior, settings inheritance, search interaction, and
knowledge/provenance semantics. Straightforward bug fixes need no new ADR.

Validate the flows at desktop and phone sizes, after reload, after switching
projects quickly, and with failed requests. Add targeted contract and policy
tests, plus journey tests; existing tests often check that individual controls
exist rather than whether a complete workflow is predictable.

Useful success measures are fewer steps for the five common journeys, no
persisted empty chats from navigation, successful settings reset/reload, file
failures that always offer recovery, and successful retrieval of known material.
Collect a baseline before choosing numeric targets.
